## User Input

```text
$ARGUMENTS
```

Вы **обязаны** учитывать ввод пользователя перед продолжением, если он не пустой. Пользователь может указать:
- `create` - создать новый `CLAUDE.md` с нуля
- `update` - улучшить существующий `CLAUDE.md`
- `audit` - проанализировать и описать качество текущего `CLAUDE.md`
- конкретный путь для создания/обновления (например, `src/api/CLAUDE.md` для инструкций на уровне каталога)

## Основные принципы

**LLM stateless**: `CLAUDE.md` — это единственный файл, который автоматически включается в каждую беседу. Он служит основным документом онбординга для AI-агентов в кодовую базу.

### Золотые правила

1. **Меньше — лучше**: современные LLM справляются примерно с 150-200 инструкциями. Системный промпт Claude Code уже использует около 50. Делайте `CLAUDE.md` кратким и сфокусированным.

2. **Универсальность**: включайте только информацию, которая нужна в КАЖДОЙ сессии. Задачно-специфичные инструкции должны лежать в отдельных файлах.

3. **Не используйте Claude как линтер**: правила стиля раздувают контекст и ухудшают следование инструкциям. Используйте детерминированные инструменты (prettier, eslint и т. п.).

4. **Никогда не генерируйте автоматически**: `CLAUDE.md` — это самая ценная точка входа в AI-harness. Создавайте его вручную и обдуманно.

## Поток выполнения

### 1. Анализ проекта

Сначала проанализируйте текущее состояние проекта:

1. Проверьте наличие существующих `CLAUDE.md`:
   - На уровне корня: `./CLAUDE.md` или `.claude/CLAUDE.md`
   - На уровне каталога: `**/CLAUDE.md`
   - Глобальная пользовательская конфигурация: `~/.claude/CLAUDE.md`

2. Определите структуру проекта:
   - Технологический стек (языки, фреймворки)
   - Тип проекта (monorepo, одно приложение, библиотека)
   - Инструменты разработки (package manager, build system, test runner)

3. Изучите существующую документацию:
   - `README.md`
   - `CONTRIBUTING.md`
   - `package.json`, `pyproject.toml`, `Cargo.toml` и т. п.

### 2. Стратегия контента (WHAT, WHY, HOW)

Структурируйте `CLAUDE.md` вокруг трёх измерений:

#### WHAT - технология и структура
- Обзор технологического стека
- Организация проекта (особенно важно для monorepo)
- Ключевые каталоги и их назначение

#### WHY - цель и контекст
- Что делает проект
- Почему были приняты те или иные архитектурные решения
- За что отвечает каждый крупный компонент

#### HOW - рабочий процесс и соглашения
- Workflow разработки (bun vs node, pip vs uv и т. д.)
- Процедуры тестирования и команды
- Способы проверки и сборки
- Критические "подводные камни" или неочевидные требования

### 3. Стратегия постепенного раскрытия

Для крупных проектов рекомендуйте создать папку `agent_docs/`:

```
agent_docs/
  |- building_the_project.md
  |- running_tests.md
  |- code_conventions.md
  |- architecture_decisions.md
```

В `CLAUDE.md` ссылайтесь на эти файлы так:
```markdown
For detailed build instructions, refer to `agent_docs/building_the_project.md`
```

**Важно**: используйте ссылки вида `file:line` вместо фрагментов кода, чтобы не тащить устаревший контекст.

### 4. Ограничения качества

При создании или обновлении `CLAUDE.md`:

1. **Целевая длина**: меньше 300 строк, в идеале меньше 100
2. **Без правил стиля**: убирайте указания по lint/format
3. **Без задачных инструкций**: переносите их в отдельные файлы
4. **Без примеров кода**: используйте ссылки на файлы
5. **Без дублирования**: не повторяйте то, что уже есть в `package.json` или `README`

### 5. Обязательные разделы

Хорошо структурированный `CLAUDE.md` должен содержать:

```markdown
# Project Name

Краткое описание в одну строку.

## Tech Stack
- Основной язык и версия
- Ключевые фреймворки/библиотеки
- База данных/хранилище, если есть

## Project Structure
[Только для monorepo или сложных структур]
- `apps/` - точки входа приложения
- `packages/` - общие библиотеки

## Development Commands
- Install: `command`
- Test: `command`
- Build: `command`

## Critical Conventions
[Только неочевидные, но важные соглашения]
- Convention 1 с кратким пояснением
- Convention 2 с кратким пояснением

## Known Issues / Gotchas
[То, что регулярно сбивает разработчиков]
- Issue 1
- Issue 2
```

### 6. Антипаттерны

**НЕ включайте:**
- Правила кодстайла (для этого есть линтеры)
- Документацию о том, как использовать Claude
- Длинные объяснения очевидных паттернов
- Скопированный код
- Общие советы вида "пишите чистый код"
- Инструкции для отдельных задач
- Сгенерированный автоматически контент
- Обширные списки TODO

### 7. Чеклист проверки

Перед финализацией проверьте:

- [ ] Меньше 300 строк, лучше меньше 100
- [ ] Каждая строка применима ко ВСЕМ сессиям
- [ ] Нет правил форматирования
- [ ] Нет фрагментов кода (используйте ссылки на файлы)
- [ ] Команды действительно работают
- [ ] Для сложных проектов используется progressive disclosure
- [ ] Документированы критические подводные камни
- [ ] Нет дублирования с `README.md`

## Формат результата

### Для `create` или по умолчанию:

1. Проанализировать проект
2. Подготовить черновик `CLAUDE.md` по структуре выше
3. Показать черновик на ревью
4. Записать файл в нужное место после утверждения

### Для `update`:

1. Прочитать существующий `CLAUDE.md`
2. Провести аудит по best practices
3. Определить:
   - Что удалить (стиль, код, задачные инструкции)
   - Что сократить
   - Чего не хватает
4. Показать изменения на ревью
5. Применить изменения после утверждения

### Для `audit`:

1. Прочитать существующий `CLAUDE.md`
2. Сформировать отчёт с:
   - Текущим количеством строк и целевым значением
   - Процентом универсально применимого контента
   - Списком найденных антипаттернов
   - Рекомендациями по улучшению
3. **Не изменять** файл, только вернуть отчёт

## Работа с AGENTS.md

Если пользователь просит создать или обновить `AGENTS.md`:

`AGENTS.md` используется для определения специализированного поведения агентов. В отличие от `CLAUDE.md` (который хранит контекст проекта), `AGENTS.md` задаёт:
- Роли и возможности агентов
- Инструкции и ограничения для конкретного агента
- Определение workflow для многоагентных сценариев

Применяйте похожие принципы:
- Делайте файл сфокусированным и кратким
- Используйте progressive disclosure
- Ссылайтесь на внешние документы, а не вставляйте их содержимое

## Примечания

- Всегда проверяйте, что команды работают, прежде чем включать их
- Если есть сомнения, лучше не добавлять
- Системное напоминание сообщает Claude, что `CLAUDE.md` "может быть или не быть релевантным" — чем больше шума, тем ниже шанс, что он будет полезен
- Monorepo особенно выигрывают от ясной структуры WHAT/WHY/HOW
- `CLAUDE.md` на уровне каталога должен быть ещё более сфокусированным
